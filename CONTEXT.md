# reax

A repository that ships an agent skill for generating, reviewing, and visually testing React UI components. The skill is shared from this repo.

## Terms

**Design system agnostic**: The skill does not assume a specific component library, token format, or styling approach. It learns the target project's conventions from its `DESIGN.md` and its existing components.

**DESIGN.md**: A markdown file in the target project, in the open DESIGN.md format: YAML design tokens (colors, type, spacing, radii, and so on) plus the format's standard sections, with Language, Component inventory and Gaps added after them. It summarizes the project's design tokens and design language. It is derived from the project's own token files, which own the values. Generated by the skill's `init` command when it is missing, and the source the skill reads before creating or reviewing components.

**COMPONENTS.md**: A markdown file in the target project, beside `DESIGN.md`, recording how its components are written: folder layout and file names, how components and props are declared, how styles select variants, prop naming and how stories are written, each with how many components follow it and the exceptions. Generated by `init` from a scan plus the agent's reading of a few components. New components and stories follow it, and `review` reports unexplained deviations from it. Its Overview and Notes belong to the person.

**Component convention**: One way the project's components are written, such as `forwardRef` or a `data-variant` attribute, counted across all components. About 70% or more makes it the convention; a closer split is mixed, and `init` asks about it or recommends the newest pattern.

**Direction**: A complete look proposed for a project with no design system: one idea from the users' own world, decided as colour, type, spacing and density, and shape and depth, with the use scene that set light or dark. The `direction` command shows three, the person picks one, and it becomes the project's token file and DESIGN.md.

**Specimen**: The page that shows directions side by side, each on the person's first screen and the core components, with palette, type, space and shape. It has no scripts and is published as a private Artifact when the person cannot open local files.

**PRODUCT.md**: A markdown file at the project root recording confirmed product truth: who uses the product, in what situation, what it is for, what makes it different, and binding brand commitments. Written by `direction`, in the format the impeccable skill also reads.

**Design sidecar**: The file `.reax/design.json` beside `DESIGN.md`, holding the data the open format cannot: the source file and real name of each token, the component conventions behind `COMPONENTS.md`, the component inventory with each component's other names, the language fields, shadows, and the scan stamps used to tell when the two files have drifted from the project.

**Fallback scale**: The set of tokens `init` proposes when a project has none for a group, named with the open format's recommended names. It is marked proposed and written to the project only after the person confirms.

**Init**: The skill command that scans the target project and writes `DESIGN.md` and the design sidecar. It never overwrites: it shows a diff and asks first, adds only its own sections to an existing `DESIGN.md`, and asks at most three questions. For an existing design system it summarizes the tokens and language it finds.

**from-figma**: The command that generates a component from a design input: an image or screenshot, or a Figma link once that connection works.

**from-text**: The command that generates a component from a plain-text description.

**Component folder**: The per-component directory the generator writes: `Name.tsx`, `Name.css` (or `Name.module.css`, or none when the project's language is utility classes), `Name.stories.tsx`, and `index.ts`. Components are co-located with their files rather than sorted by file type.

**Review**: The command that audits existing components against `DESIGN.md` and the mobile-first and AI-usability goals.

**Visual test**: The automated checks on a component's Storybook stories, run with Playwright: a screenshot pixel comparison and an accessibility scan. It writes a text report with a list of improvements, and can open the Preview afterwards.

**Capture**: One screenshot of a story at one width and text size. A visual test takes four per story: 390 pixels wide, 1280 wide, 320 wide to check reflow, and 390 wide with text at 200%.

**Baseline**: The approved reference captures that a later visual test is compared with. A person approves them, and only after the visual review has passed. A first run with no baseline fails nothing.

**Preview**: The local live page, opened from the visual test, where a person uses a built component by hand. It has four modes (test, comment, anatomy, edit), a resizable frame, and a sweep that finds the narrowest width at which the component still works. It renders the project's stories in Storybook's own preview frame, which a local helper starts and serves beside the page. The page ships with the skill and the helper serves it; the only things it writes into the project are comments, applied edits and pinned widths.

**Screenshot gallery**: The page every visual test writes beside its report, showing each story's captures and result. It is published as a private Artifact when the person cannot reach the Preview, for example in a cloud session.

**Comment**: A note a person attaches to a selected element in the Preview. It records the text, the story, the viewport and text scale, the element's selector, role, accessible name, position and size, a cropped screenshot, and a status (open, addressed, resolved). Only the person marks a comment resolved.

**Anatomy mode**: The Preview mode that shows how a component is built: its numbered parts, props with their current values, the tokens it uses, and an accessibility view.

**Edit mode**: The Preview mode where a person changes text, variants and token-based values as a live draft, then applies one change set that the agent writes to code using the tokens in `DESIGN.md`. Accessibility problems show while editing, and applying them needs explicit acceptance.

**Slot**: A named part of a component, marked in generated code with `data-slot` and named in the component card.

**Visual review**: Claude's judgement of the screenshots of a component's rendered stories against `DESIGN.md` and the component card, reported as text. The screenshots are also left for the user to confirm.

**Component card**: A short per-component specification the skill loads on demand: anatomy, props, variants, states, accessibility requirements, mobile behaviour and review checks. Both generation and review read the same card.

**Requirement**: An accessibility rule in a component card or the shared rules that comes from WCAG 2.2 AA and cites its success criterion. Nothing overrides it, except an exception a person explicitly accepts in Edit mode, which is recorded.

**Default**: A rule in a component card or the shared rules that is the skill's own choice, not a WCAG success criterion. A request or the project overrides it.

**Default ruling**: The choice the skill applies where authoritative sources disagree. A project can override it, except for accessibility requirements, which always apply.

**Alias map**: The list linking each component's other names (for example Modal, Dialog, Popup) to one canonical name, so a project's own names resolve to the right component card.
